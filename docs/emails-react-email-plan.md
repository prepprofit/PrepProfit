# Plan - React Email migration + Weekly CFO Report email

Status: **READY FOR DEV SLICING after stack approval. Not implemented.**
Reviewed: 2026-07-02.
Source reviewed against: `PrepProfit-main (37).zip`.

This replaces the earlier draft. The main changes are:

- Use React Email for all email **HTML bodies**, but keep the existing `EmailSender`
  seam and Resend SDK wrapper.
- Reuse the existing `email_outbox` worker for the Weekly CFO Report email instead of
  direct cron sends, so retries and durable dedupe remain database-backed.
- Ship the Weekly CFO email as a deterministic report first. Do **not** run the AI
  narrative from cron in this slice; the existing AI meter is user-actor based and the
  product should not silently spend a user's AI allowance from an automated job.
- Keep PDF generation on `@react-pdf/renderer` untouched.

Implementation references:

- React Email render utility: https://react.email/docs/utilities/render
- React Email Tailwind component and limitations: https://react.email/docs/components/tailwind
- React Email CLI preview: https://react.email/docs/cli
- Resend send API/idempotency header: https://resend.com/docs/api-reference/emails/send-email

## 0. Goal

1. Adopt the React Email "Barebone" visual language as PrepProfit's house email
   style: quiet boxed layout, clear header, simple cards/tables, restrained footer.
2. Migrate every existing hand-built HTML email body to React Email components.
3. Add the Weekly CFO Report email as an opt-in, manager-facing weekly digest.
4. Preserve the current security posture: org isolation, i18n, audit rules, retry
   semantics, no accidental cross-tenant reads, no API-key logging.

Non-goals:

- Do not change the PDF renderers for invoices, P&L, recipe cards, or purchase orders.
- Do not introduce Resend Templates or hosted template editing.
- Do not send the CFO AI write-up automatically in the weekly email.
- Do not change recipient discovery to scrape member emails.

## 1. Stack approval and dependency decision

React Email is a stack addition and needs explicit approval under `CLAUDE.md`.

Recommended dependency shape:

- Runtime deps: `@react-email/components` and `@react-email/render`, exact-pinned.
- Optional dev-only preview tooling: add `react-email` CLI only if the team wants
  `npm run email:dev`. Keep template runtime imports on the scoped packages so the
  production server bundle depends on the narrow runtime packages.
- Install only after verifying the selected versions support React 19 / React DOM 19.
  Current package metadata for the scoped packages declares React 18/19 peer support,
  but the implementing dev must verify against the exact version npm resolves.

Import rule:

- Do not mix `react-email` and `@react-email/*` imports in templates. Pick the scoped
  runtime imports and use them consistently.
- Do not copy canary demo imports blindly. Port the Barebone theme and structure into
  stable package APIs.

Why not send `react: <Email />` directly through Resend?

- The app already has a small `EmailSender.send({ html, attachments })` seam used by
  tests, webhooks, actions, and the outbox worker.
- Rendering to `{ html, text }` inside PrepProfit keeps tests deterministic and avoids
  coupling the rest of the app to Resend's React payload behavior.

Small seam extension allowed:

- Add optional `text?: string` to `SendEmailInput` and pass it to Resend when present.
  Existing callers keep working. New React Email callers should pass both HTML and
  plain text for better accessibility/deliverability.

## 3. Shared React Email architecture

Add an `emails/` directory at repo root, because React Email preview tooling expects
that convention.

Recommended structure:

```txt
emails/
  _components/
    BaseEmail.tsx
    Card.tsx
    CtaButton.tsx
    Footer.tsx
    KeyValueTable.tsx
    theme.ts
    theme-fonts.tsx
  WelcomeEmail.tsx
  SubscriptionEmail.tsx
  PaymentPastDueEmail.tsx
  LowStockEmail.tsx
  DocumentEmail.tsx
  PurchaseOrderEmail.tsx
  AiCostReportEmail.tsx
  CfoReportEmail.tsx
```

Rendering helper:

```txt
lib/email/render.tsx
```

Responsibilities:

- Export `renderEmail(element): Promise<{ html: string; text: string }>` using React
  Email render utilities.
- Ensure this helper is server-only. Do not import `emails/*` from client components.
- Tests should use the same helper instead of snapshotting raw JSX output.

Base shell:

- `BaseEmail` owns `<Html>`, `<Head>`, fonts, `<Preview>`, `<Body>`, outer background,
  container, header, footer, and optional CTA.
- Templates receive copy and values as props. They should not call `getTranslations`.
- Use React children for all untrusted strings. No `dangerouslySetInnerHTML`.
- Use simple layout primitives that are known to survive email clients: sections,
  rows, columns, tables, inline styles/Tailwind classes that React Email can inline.

Tailwind/theme:

- Port the Barebone palette/scale into `emails/_components/theme.ts`, rethemed to
  PrepProfit's accent.
- Use React Email's `<Tailwind>` with `pixelBasedPreset`.
- Keep class usage simple. The React Email Tailwind docs call out limitations around
  complex selectors and utilities like `space-*`; do not rely on those in emails.
- The email theme is not the app's Tailwind config. Treat it as a small email-specific
  design system.

## 4. Copy, i18n, and escaping rules

CLAUDE.md rule stays: user-visible copy comes from `next-intl`.

Pattern:

- Sender/action/route resolves translations in server code.
- Template receives already-translated strings and preformatted values as props.
- Template files may contain only structural/non-user copy if unavoidable, but the bar
  should be "no literal recipient-facing prose in templates."

React escaping rule:

- React escapes text nodes, but only if values are passed as children/props.
- Do not use `dangerouslySetInnerHTML`.
- Do not build HTML fragments in strings and pass them into templates.
- For URLs, validate/normalize before passing to `href`/`src`. Never pass user input
  directly as a URL.

Existing `escapeHtml()` helpers can be removed only after the relevant sender no longer
interpolates user data into HTML strings.

## 5. Assets, links, and `APP_URL`

Add a narrow lazy env helper for email URLs, not part of `serverEnvSchema`:

```txt
APP_URL
```

Rules:

- Validate as an absolute `https://` URL in production. Localhost can be allowed in
  development/tests.
- Strip trailing slash in the helper.
- If missing or invalid, email rendering must not crash unrelated pages.
- If `APP_URL` is unavailable, render a logo-less header and omit CTAs that need an
  absolute app link.

Assets:

- Put brand email assets in `public/static/emails/`.
- Production email asset URLs are `${APP_URL}/static/emails/...`.
- React Email preview can use its own local static serving, but sent emails need
  publicly reachable absolute URLs.
- Do not include the Barebone marketing hero/feature images. Transactional/report
  email should stay compact and inspectable.

Recommended CTAs:

- Billing/subscription/past-due emails: billing/settings URL only if `APP_URL` exists.
- CFO report email: `/reports/cfo?weekTo=YYYY-MM-DD` only if `APP_URL` exists.
- Low-stock email: optional inventory link only if `APP_URL` exists.

- Add a system-job helper that resolves a tier for an arbitrary org, fail-closed:

- The mirror is still not a request-time entitlement source. This helper is only for
  system jobs deciding whether to enqueue optional outbound reports.

Enqueue route:

- Add `app/api/cron/cfo-report/route.ts`.
- Auth/rate-limit like the other cron routes.
- Iterate Clerk organizations by page.
- For each org, inside `withOrg`:
  - read settings;
  - skip if opt-in off;
  - skip if no `businessEmail`;
  - skip if tier is starter;
  - load `loadCfoReport(tx, org.id, defaultCfoWeekTo(now))`;
  - skip if `!report.hasData`;
  - enqueue one row:
    - `documentType: 'cfo_report'`
    - `documentId: weekTo`
    - `toEmail: settings.businessEmail`
    - `subject: translated CFO subject`
    - `dedupKey: cfo_report:${weekTo}`
- The unique `(org, dedupKey)` makes re-running the weekly enqueue idempotent.

Scheduling:

- Existing `process-email-outbox` runs daily at `04:30 UTC`.
- Schedule the CFO enqueue before it, for example Monday `04:00 UTC`, or update the
  outbox worker frequency in a separate reviewed ops decision.

## 7. Weekly CFO Report email product spec

Recipient:

- `organization_settings.businessEmail`.
- No member scraping.
- No CC/BCC in MVP.

Access/data class:

- Financial, manager-facing.
- Send only to opted-in orgs on Pro/Business-equivalent tiers.
- Starter always skipped.

Content:

- Period range.
- Revenue trend.
- Food-cost trend, including partial-data note.
- Top margin leaks.
- Reprice candidates.
- Supplier price changes.
- Low stock.
- Confidence notes.
- CTA to open the report in the app when `APP_URL` is configured.

AI narrative:

- Not included in MVP automated email.
- Reason: current `ai_operation_attempts.actor_user_id` is non-null and the existing
  Server Action is deliberately user-initiated. Automated quota spending needs its
  own product approval and ledger design.
- The email can include a CTA to open the CFO report and generate the AI write-up in
  the app, where the manager explicitly spends a quota unit.

Future AI email narrative, if approved later:

- Add a second explicit setting such as `weekly_cfo_report_ai_email_enabled`.
- Decide whether system AI attempts use nullable `actorUserId` or a separate system
  actor field.
- Keep quota reservation race-safe with `lockMonthlyOperationQuota`.
- Never block deterministic email delivery on provider failure.

CFO enqueue tests:

- Opt-in OFF -> no outbox row.
- Missing business email -> no outbox row.
- Starter/missing plan mirror -> no outbox row.
- Pro/Business + data -> one outbox row.
- Re-running same week -> no duplicate row.
- Per-org work runs inside `withOrg`.

CFO delivery tests:

- Claimed `cfo_report` row renders and sends deterministic report.
- Provider failure marks failed/backoff and no audit send event.
- Provider success marks sent, records `providerMessageId`, and audits safe metadata.
- Resend idempotency key equals row dedup key.
- No AI provider call happens during automated email delivery.

Regression tests:

- Existing purchase-order outbox behavior remains unchanged.
- Existing document email action still audits only after provider acceptance.
- Existing low-stock cron still skips quietly when email is not configured.

## 9. Risk register

| Risk | Mitigation |
|------|------------|
| React Email package/API drift | Exact-pin versions, verify React 19 peers before install, keep imports consistent. |
| Email CSS differs from app Tailwind | Maintain a small email-only theme; avoid complex Tailwind selectors. |
| Raw HTML injection sneaks back | Ban `dangerouslySetInnerHTML`; test hostile strings per template. |
| CFO duplicate sends | Use outbox unique dedup row and `provider_message_id`; Resend idempotency is secondary only. |
| Cron uses request-bound entitlements | Add cron-safe tier resolver; fail closed to starter. |
| Automated AI spend surprises customers | Do not include AI narrative in MVP email. CTA sends managers to the app for explicit generation. |
| `APP_URL` missing in production | Render logo-less/no-CTA fallback; document env var in ops docs. |
| Settings toggle leaks financial report to wrong address | Use only `businessEmail`, show that in UI, and skip send if blank. |
| Outbox worker becomes too branchy | Split delivery functions by document type and keep shared claim/mark logic unchanged. |
